Working with Associations

Doctrine hydrator is especially useful when dealing with associations (OneToOne, ManyToOne, OneToMany and ManyToMany). This page shows how associated entities are hydrated and extracted, and how this can be configured. For complete examples, see Example Usage with Laminas Form and Example Usage in an API Context.

OneToOne and ManyToOne Associations

A simple example with BlogPost and User entities to illustrate a ManyToOne association:

namespace Application\Entity;use Doctrine\ORM\Mapping as ORM;#[ORM\Entity]class User{    #[ORM\Id]    #[ORM\Column(type: 'integer')]    #[ORM\GeneratedValue(strategy: 'AUTO')]    private ?int $id = null;    #[ORM\Column(type: 'string', length: 48)]    private ?string $username = null;    #[ORM\Column(type: 'string')]    private ?string $password = null;    public function getId(): ?int    {        return $this->id;    }    public function setUsername(string $username): void    {        $this->username = $username;    }    public function getUsername(): ?string    {        return $this->username;    }    public function setPassword(string $password): void    {        $this->password = $password;    }    public function getPassword(): ?string    {        return $this->password;    }}

And the BlogPost entity, with a ManyToOne association:

namespace Application\Entity;use Doctrine\ORM\Mapping as ORM;#[ORM\Entity]class BlogPost{    #[ORM\Id]    #[ORM\Column(type: 'integer')]    #[ORM\GeneratedValue(strategy: 'AUTO')]    private ?int $id = null;    #[ORM\ManyToOne(targetEntity: User::class)]    private ?User $user = null;    #[ORM\Column(type: 'string')]    private ?string $title = null;    public function getId(): ?int    {        return $this->id;    }    public function setUser(User $user): void    {        $this->user = $user;    }    public function getUser(): ?User    {        return $this->user;    }    public function setTitle(string $title): void    {        $this->title = $title;    }    public function getTitle(): ?string    {        return $this->title;    }}

There are two use cases that can arise when using OneToOne and ManyToOne associations: the toOne entity (in this case, the User) may already exist (which will often be the case with a User and BlogPost example), or it needs to be created. The Doctrine hydrator natively supports both cases.

Existing Entity in the Association

When the association’s entity already exists, all you need to do is give the identifier of the association:

use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;$hydrator = new DoctrineHydrator($entityManager);$blogPost = new BlogPost();$data = [    'title' => 'The best blog post in the world!',    'user'  => [        'id' => 2, // Written by user 2    ],];$blogPost = $hydrator->hydrate($data, $blogPost);echo $blogPost->getTitle(); // prints "The best blog post in the world!"echo $blogPost->getUser()->getId(); // prints 2

NOTE : when using association whose primary key is not compound, you can rewrite the following more succinctly:

$data = [    'title' => 'The best blog post in the world!',    'user'  => [        'id' => 2, // Written by user 2    ],];

to:

$data = [    'title' => 'The best blog post in the world!',    'user'  => 2,];

Non-existing Entity in the Association

If the association’s entity does not exist, you just need to provide the actual object to the hydrator:

use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;$hydrator = new DoctrineHydrator($entityManager);$blogPost = new BlogPost();$user = new User();$user->setUsername('bakura');$user->setPassword('p@$$w0rd');$data = [    'title' => 'The best blog post in the world!',    'user'  => $user,];$blogPost = $hydrator->hydrate($data, $blogPost);echo $blogPost->getTitle(); // prints "The best blog post in the world!"echo $blogPost->getUser()->getUsername(); // prints "bakura"

For this to work, you must also slightly change your mapping, so that Doctrine can persist new entities on associations (note the cascade options on the ManyToOne association):

namespace Application\Entity;use Doctrine\ORM\Mapping as ORM;#[ORM\Entity]class BlogPost{    /** … */    #[ORM\ManyToOne(targetEntity: User::class, cascade: ['persist'])]    private ?User $user = null;    /** … */}

It’s also possible to provide the User data as a nested array. The hydrator will use the mapping data to determine the identifiers for the toOne relation and either attempt to find the existing record or instantiate a new target instance which will be hydrated before it is passed to the BlogPost entity. The nested data is hydrated by a separate hydrator, see Configuring Associated Entities.

Adding users via a blog post is not recommended.

 
use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;$hydrator = new DoctrineHydrator($entityManager);$blogPost = new BlogPost();$data = [    'title' => 'Art thou mad?',    'user' => [        'id' => '',        'username' => 'willshakes',        'password' => '2BorN0t2B',    ],];$blogPost = $hydrator->hydrate($data, $blogPost);echo $blogPost->getUser()->getUsername(); // prints willshakesecho $blogPost->getUser()->getPassword(); // prints 2BorN0t2B

Creating New Associated Entities

By default, new associated entities are created by calling their constructor without arguments, before they are hydrated with the data. This applies to OneToOne and ManyToOne associations as well as to collections. If the constructor of an entity requires arguments, pass a closure creating the entities to the hydrator. The closure receives the class name and the data the entity will be hydrated with:

use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;$hydrator = new DoctrineHydrator(    $entityManager,    instantiator: static fn (string $className, array $data): object => match ($className) {        User::class => new User($data['username']),        default => new $className(),    },);

The closure must return an instance of the given class. To create entities without calling their constructor, as Doctrine does when loading entities, you can use doctrine/instantiator:

use Doctrine\Instantiator\Instantiator;$instantiator = new Instantiator();$hydrator     = new DoctrineHydrator(    $entityManager,    instantiator: static fn (string $className): object => $instantiator->instantiate($className),);

Note that collections and other properties initialized in the constructor are not initialized then. The instantiator is inherited by the hydrators of associated entities, see Configuring Associated Entities.

Handling of Null Values

When a null value is passed to a OneToOne or ManyToOne field, for example:

$data = [    'user' => null,];

The hydrator will check whether the setUser() method on the entity allows null values and act accordingly. The following describes the process that happens when a null value is received:

  1. If the setUser() method DOES NOT allow null values i.e. function setUser(User $user), the null is silently ignored and will not be hydrated.
  2. If the setUser() method DOES allow null values i.e. function setUser(?User $user), the null value will be hydrated.

When hydrating by reference, the type of the $user property is checked the same way: for private User $user, the null is silently ignored, while for private ?User $user (or an untyped property) the null value will be hydrated.

OneToMany and ManyToMany Associations

Collections of OneToMany and ManyToMany associations are hydrated the same way, the following examples use a OneToMany association. In Laminas forms, collections are typically represented by a Laminas\Form\Element\Collection element, see the Laminas documentation to learn more about Collection elements.

Internally, for a given collection, if an array contains identifiers, the hydrator automatically fetches the objects through the Doctrine find function. Empty values, like the empty string submitted by a form for a new element, are looked up the same way, and are ignored if no entity is found for them. Avoid empty values as primary keys, which should not happen if you use auto-increment primary keys, anyway.

For example, consider the following BlogPost and Tag entities:

namespace Application\Entity;use Doctrine\Common\Collections\ArrayCollection;use Doctrine\Common\Collections\Collection;use Doctrine\ORM\Mapping as ORM;#[ORM\Entity]class BlogPost{    #[ORM\Id]    #[ORM\Column(type: 'integer')]    #[ORM\GeneratedValue(strategy: 'AUTO')]    private ?int $id = null;    #[ORM\OneToMany(targetEntity: Tag::class, mappedBy: 'blogPost')]    private Collection $tags;    /**     * Never forget to initialize your collections!     */    public function __construct()    {        $this->tags = new ArrayCollection();    }    public function getId(): ?int    {        return $this->id;    }    public function addTags(Collection $tags): void    {        foreach ($tags as $tag) {            $tag->setBlogPost($this);            $this->tags->add($tag);        }    }    public function removeTags(Collection $tags): void    {        foreach ($tags as $tag) {            $tag->setBlogPost(null);            $this->tags->removeElement($tag);        }    }    public function getTags(): Collection    {        return $this->tags;    }}

And the Tag entity:

namespace Application\Entity;use Doctrine\ORM\Mapping as ORM;#[ORM\Entity]class Tag{    #[ORM\Id]    #[ORM\Column(type: 'integer')]    #[ORM\GeneratedValue(strategy: 'AUTO')]    private ?int $id = null;    #[ORM\ManyToOne(targetEntity: BlogPost::class, inversedBy: 'tags')]    private ?BlogPost $blogPost = null;    #[ORM\Column(type: 'string')]    private ?string $name = null;    public function getId(): ?int    {        return $this->id;    }    /**     * Allow null to remove association     */    public function setBlogPost(?BlogPost $blogPost = null): void    {        $this->blogPost = $blogPost;    }    public function getBlogPost(): ?BlogPost    {        return $this->blogPost;    }    public function setName(string $name): void    {        $this->name = $name;    }    public function getName(): ?string    {        return $this->name;    }}

Please note some interesting things in the BlogPost entity. There are defined two functions: addTags and removeTags. When hydrating by value (the default), those functions must be defined and are called automatically by the Doctrine hydrator when dealing with collections. This is not overkill and is preferred to just a setTags function to replace the old collection with a new one:

public function setTags(Collection $tags): void{    $this->tags = $tags;}

This is considered a bad design because Doctrine collections should not be swapped; mostly because collections are managed by an object manager and must not be replaced by a new instance. See Collection Strategies for how adders and removers are used.

Once again, two cases may arise: the tags already exist or they do not.

Existing Entities in the Association

When the association’s entities already exist, just provide the identifiers of these entities:

use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;$hydrator = new DoctrineHydrator($entityManager);$blogPost = new BlogPost();$data = [    'tags'  => [        ['id' => 3], // add tag whose id is 3        ['id' => 8], // also add tag whose id is 8    ],];$blogPost = $hydrator->hydrate($data, $blogPost);echo count($blogPost->getTags()); // prints 2

Note, again, that

$data = [    'tags'  => [        ['id' => 3], // add tag whose id is 3        ['id' => 8], // also add tag whose id is 8    ],];

can be written:

$data = [    'tags'  => [3, 8],];

Non-existing Entities in the Association

If the association’s entities do not exist, you need to provide the actual objects:

use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;$hydrator = new DoctrineHydrator($entityManager);$blogPost = new BlogPost();$tags = [];$tag1 = new Tag();$tag1->setName('PHP');$tags[] = $tag1;$tag2 = new Tag();$tag2->setName('STL');$tags[] = $tag2;$data = [    'tags'  => $tags, // Note that you can mix integers and entities without any problem];$blogPost = $hydrator->hydrate($data, $blogPost);echo count($blogPost->getTags()); // prints 2

For this to work, you must also slightly change your mapping, so that Doctrine can persist new entities on associations (note the cascade options on the OneToMany association):

namespace Application\Entity;use Doctrine\Common\Collections\Collection;use Doctrine\ORM\Mapping as ORM;#[ORM\Entity]class BlogPost{    /** … */    #[ORM\OneToMany(targetEntity: Tag::class, mappedBy: 'blogPost', cascade: ['persist'])]    private Collection $tags;    /** … */}

Collection Strategies

By default, every collection association has a strategy attached to it that is called during the hydrating and extracting phase. Strategies for collection associations must implement Doctrine\Laminas\Hydrator\Strategy\CollectionStrategyInterface, otherwise an InvalidArgumentException is thrown. All strategies provided by this library extend from the class Doctrine\Laminas\Hydrator\Strategy\AbstractCollectionStrategy.

The library provides four strategies out of the box:

  1. Doctrine\Laminas\Hydrator\Strategy\AllowRemoveByValue: this is the default strategy; it removes old elements that are not in the new collection.
  2. Doctrine\Laminas\Hydrator\Strategy\AllowRemoveByReference: this is the default strategy if set to byReference; it removes old elements that are not in the new collection.
  3. Doctrine\Laminas\Hydrator\Strategy\DisallowRemoveByValue: this strategy does not remove old elements even if they are not in the new collection.
  4. Doctrine\Laminas\Hydrator\Strategy\DisallowRemoveByReference: this strategy does not remove old elements even if they are not in the new collection.

As a consequence, when using AllowRemove*, you need to define both adder (eg. addTags) and remover (eg. removeTags). On the other hand, when using the DisallowRemove* strategy, you must always define at least the adder, but the remover is optional (because elements are never removed).

The following table illustrates the difference between the two strategies:

Strategy Initial collection Submitted collection Result
AllowRemove* A, B B, C B, C
DisallowRemove* A, B B, C A, B, C

The difference between ByValue and ByReference is that, when using strategies that end with ByReference, it won’t use the public API of your entity (adder and remover) - you don’t even need to define them - it will add and remove elements directly from the collection.

Changing the Strategy

Changing the strategy for collections is simple:

use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;use Doctrine\Laminas\Hydrator\Strategy;$hydrator = new DoctrineHydrator($entityManager);$hydrator->addStrategy('tags', new Strategy\DisallowRemoveByValue());

The strategies derive the names of adders and removers, e.g. addTags() and removeTags(), using an inflector. To use a custom inflector, pass it to the constructor of the strategy, e.g. new Strategy\DisallowRemoveByValue($inflector). Strategies added automatically, as configured by the default strategies below, use the default inflector.

To change the strategy for all collections of a hydrator, including the collections of associated entities, set the default strategy instead:

$hydrator->setDefaultByValueStrategy(Strategy\DisallowRemoveByValue::class);$hydrator->setDefaultByReferenceStrategy(Strategy\DisallowRemoveByReference::class);

Strategies added with addStrategy() only apply to the entity passed to the hydrator. For collections of associated entities, add them to the hydrator of the associated class, see Configuring Associated Entities.

Strategies for other fields are described in Basic Usage.

Custom Strategies

A custom strategy for collections can extend AbstractCollectionStrategy and implement the hydrate() method:

use Doctrine\Laminas\Hydrator\Strategy\AbstractCollectionStrategy;final class MyCollectionStrategy extends AbstractCollectionStrategy{    public function hydrate(mixed $value, ?array $data = null): mixed    {        $collection = $this->getCollectionFromObjectByValue();        // … add and remove elements of $collection based on $value …        return $collection;    }}

Extracting Associations

By default, extract() returns associations as they are: a OneToOne or ManyToOne association is returned as the associated entity (which may be an uninitialized proxy), a OneToMany or ManyToMany association as the collection (e.g. a PersistentCollection). This is exactly what Laminas forms need to bind nested fieldsets to the associated entities, see Example Usage with Laminas Form.

When you need plain data instead, for instance to serialize an entity to JSON, you can change how associations are extracted:

use Doctrine\Laminas\Hydrator\AssociationExtraction;use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;$hydrator = new DoctrineHydrator($entityManager);$hydrator->setAssociationExtraction(AssociationExtraction::Identifier);

The following modes are available:

Mode Extracted associations
AssociationExtraction::Object Entities and collections as they are (default).
AssociationExtraction::Identifier Identifiers of the associated entities.
AssociationExtraction::Array Associated entities extracted into nested arrays.

The following examples use a BlogPost with both the user and the tags association from the sections above.

Identifiers

With AssociationExtraction::Identifier, each associated entity is replaced by its identifier, collections become arrays of identifiers:

$hydrator->setAssociationExtraction(AssociationExtraction::Identifier);$data = $hydrator->extract($blogPost);// [//     'id'    => 5,//     'title' => 'The best blog post in the world!',//     'user'  => 2,//     'tags'  => [3, 8],// ]

Entities with a composite identifier are extracted as an array of their identifier fields, e.g. ['country' => 'DE', 'code' => '48149']. An empty OneToOne or ManyToOne association is extracted as null.

Nested Arrays

With AssociationExtraction::Array, associated entities are extracted into arrays themselves:

$hydrator->setAssociationExtraction(AssociationExtraction::Array);$data = $hydrator->extract($blogPost);// [//     'id'    => 5,//     'title' => 'The best blog post in the world!',//     'user'  => ['id' => 2, 'username' => 'bakura', 'password' => 'p@$$w0rd'],//     'tags'  => [//         ['id' => 3, 'name' => 'PHP', 'blogPost' => 5],//         ['id' => 8, 'name' => 'STL', 'blogPost' => 5],//     ],// ]

By default, only the associations of the extracted entity are converted to arrays; associations of nested entities are extracted as identifiers. Pass the maximum depth as second argument to extract more levels:

$hydrator->setAssociationExtraction(AssociationExtraction::Array, 3);

Circular references are detected: an entity that is already being extracted further up, like the blog post of each tag above, is extracted as its identifier, regardless of the maximum depth.

Associated entities are extracted by separate hydrators. Strategies and filters added to your hydrator only apply to the extracted entity itself. To exclude fields of associated entities, like the password of the user above, configure the hydrator used for them, see Configuring Associated Entities:

use Doctrine\Laminas\Hydrator\Filter\PropertyName;$hydrator->getAssociationHydrator(User::class)->addFilter('password', new PropertyName(['password']));

Further Notes

  • Values that a strategy has already converted are left untouched; only instances of the association's target entity are converted.
  • Keys of collections are preserved, which matters for collections indexed by a field.
  • Embeddables are no associations, how they are extracted is configured separately, see Embeddables as Arrays.
  • The extracted data can be passed to hydrate() again, as the hydrator accepts both identifiers and nested arrays for associations.
  • Extracting associations as arrays loads the associated entities from the database, see Performance Considerations.

Configuring Associated Entities

Strategies and filters of a hydrator refer to the fields of an entity. Therefore, they only apply to the entity passed to hydrate() or extract(). Associated entities are hydrated and extracted by separate hydrators, one per entity class, which are used at all levels of associations.

These association hydrators are used in two cases:

  • When hydrating data containing nested arrays for an association, like ['user' => ['username' => 'willshakes']]. Identifiers and objects given for an association do not need to be hydrated.
  • When extracting associations with AssociationExtraction::Array.

Association hydrators are always configured on the hydrator you call hydrate() or extract() on. Note that the entity passed to hydrate() or extract() is always handled by your hydrator itself, even if an association hydrator is configured for its class.

When using Laminas forms, nested fieldsets hydrate and extract their objects with their own hydrators, so association hydrators are usually not involved there, see Example Usage with Laminas Form.

Configuring the Hydrator of a Class

To configure the hydrator for entities of a class, retrieve it with getAssociationHydrator(). It is created on first use, and the same hydrator is returned for the class afterwards:

use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;use Doctrine\Laminas\Hydrator\Filter\PropertyName;$hydrator = new DoctrineHydrator($entityManager);// Applies to the blog post passed to hydrate() or extract()$hydrator->addStrategy('title', new TitleStrategy());// Applies to every user associated with the blog post, at any level$hydrator->getAssociationHydrator(User::class)    ->addFilter('password', new PropertyName(['password']));

Association hydrators inherit the following settings from your hydrator: the object manager, hydrating by value or by reference, the inflector, the type converter, the instantiator, the default strategies for collections and the naming strategy. Settings changed on your hydrator later on apply as well. Strategies and filters are not inherited. The naming strategy can be changed or removed on an association hydrator, and the way associations and embeddables are represented in the data is always determined by the hydrator hydrate() or extract() is called on.

Replacing the Hydrator of a Class

Settings passed to the constructor, like hydrating by value or by reference or the type converter, cannot be changed on an existing hydrator. To use different ones for entities of a class, create a hydrator and set it with setAssociationHydrator():

use Doctrine\Laminas\Hydrator\DoctrineObject as DoctrineHydrator;$hydrator = new DoctrineHydrator($entityManager);// Tags are hydrated by reference, while the blog post is hydrated by value$tagHydrator = new DoctrineHydrator($entityManager, false);$tagHydrator->addStrategy('name', new TagNameStrategy());$hydrator->setAssociationHydrator(Tag::class, $tagHydrator);

A hydrator set this way keeps its own settings and only inherits the naming strategy, unless a naming strategy is set on it. It is used for entities of the class at all levels, and uses the association hydrators of your hydrator for its own associations. Therefore, configure all association hydrators on your hydrator: setting a hydrator that has association hydrators itself, or setting your hydrator as association hydrator, causes an InvalidArgumentException.
